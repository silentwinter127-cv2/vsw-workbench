# 横向视觉搜索工作台 · Visual Search Workbench

给定一张图片，快速找到更多视觉变体、不同转载源、潜在原始来源，以及原本没想到的相关图片。

这不是图片收藏站，也不是又一个「以图搜图」网页。它是**把一次次零散的识图操作，变成一个可管理、可比较、可迭代的批量工作流**：
搜索引擎负责发现，工作台负责调度、去重、排序和积累知识。

```
种子图片池 → 同图检索 → 邻域检索 → 结果合并去重 → 发现新种子 →（回到队列）
                                              ↑                    │
                                              └────────────────────┘
```

---

## 一、先说要紧的前提：本机实测的引擎边界

设计之前把「能不能直接调百度识图」这件事先测了一遍，结论决定了整个架构：

| 尝试 | 实测结果 |
| --- | --- |
| `POST graph.baidu.com/upload`（选图上传接口） | `{"status":1,"msg":"Reject"}` —— 接口被墙 |
| `graph.baidu.com/upload?image=<URL>`（按图 URL） | 读取超时 |
| `image.baidu.com/search/index?objurl=<URL>` | 302 到 `wappass.baidu.com/.../captcha/tuxing_v2.html`（验证码） |
| Bing `...&q=imgurl:<URL>` 深链 | 参数被当普通文字搜索丢弃（跳到 `q=世界旅游胜地`） |
| Bing `images/searchbyimage/upload` | **404**，接口已下线 |
| Bing `visualsearch` 上传图片 | 把图送去 **OCR** 再跳文字搜索（`qt=txt`），不是视觉检索 |
| 搜狗图片 | 页面没有公开上传入口（`fileInputs=0`） |
| Google Lens / TinEye / SauceNAO | 连接超时 / TLS 握手失败 |

于是工作台有两条并行的工作方式：

1. **自动识图（真浏览器）**：工作台开一个无头 Chromium，用 CDP `DOM.setFileInputFiles` 把变体文件
   交给引擎**自己的上传框**，页面自己完成签名上传，然后读结果页 DOM —— 这条路上**百度实测可用**，
   360 可用但会被验证码挡。全程不需要人点。
2. **手动派发 + 回填**：其余引擎一键打开入口，你把结果页内容（全选复制）或 URL 粘回来，
   工作台负责下载、三层去重、聚类、排序、来源聚合。

两条路的结果走**完全一样**的下游管线（去重/聚类/打分/回流）。引擎的可自动化程度是探测出来的，
不是假设的；详细证据与各引擎当前状态见 [`NOTES-engines.md`](NOTES-engines.md)。

## 二、六个核心功能，对应到实现

### 1. 一图多变体生成器（`vsw/imaging.py`）

导入一张图，自动生成 16 个可独立检索的查询版本，每个变体有独立 ID 并保留父图关系：

| 组 | 变体 |
| --- | --- |
| 基准 | 全图 |
| 几何 | 中心裁剪 70% / 50%、左上·右上·左下·右下四分之一、主体局部放大 2×、顶部条带 25%、底部条带 25%、**手工框选（任意矩形）** |
| 色调 | 灰度、亮度 +25%、亮度 −25%、对比度 +30% |
| 画质 | 锐化、边缘图 |

顺序不是随意的：先做最常打破死路的几何变体。每个变体都记录**是哪一种处理产生了有效结果**（见「按变体看产出」报表），这样经验操作才能变成可复现的流程。

**框选搜索（手工选区）**：种子卡片上的「框选搜索」打开一个 Lens 风格的选图面板 —— 进面板就给一个居中的选区框，
拖动即可改（四角括号 + 八向手柄 + 放大镜，框外自动压暗），可锁 1:1 / 4:3 / 3:4 / 16:9，
可选**外扩内边距**（+15% / +35% / +60%，虚线预览会显示实际送进引擎的范围），小选区还能自动放大 2× 再检索。
确认后它生成一个独立的 `crop` 变体（记录像素矩形 + 归一化坐标 + 外扩比例 + 放大倍数），
然后「仅入队」或「框选识图」（直接跑自动识图）。这意味着：

- 框选和自动变体走**完全一样**的队列 → 三层去重 → 打分 → 回放链路；
- 「搜索链回放」里会显示「手工框选（crop）」这一步，「按变体看产出」里 `crop` 单独一行；
- 所以「哪一种框法真的有效」是可比的，而不是靠记忆。

面板下方会列出该种子已有的全部框选，点一下就载回原框继续微调。另外：**如果你框的正好是引擎会返回的那块内容，
它会被判为重复载体**（`visual:own-crop`），不会冒充新发现。

### 2. 多查询批处理队列（`vsw/service.py` + `vsw/server.py` + `vsw/cdp_driver.js`）

种子 × 引擎 × 变体的笛卡尔积统一入队，状态机为 `待搜索 / 搜索中 / 待复查 / 已完成 / 失败`。
每条队列项有两条出路：

- **自动识图**（百度 / 360）：工作台开无头浏览器，把变体文件交给引擎的上传框，读回结果页入库，
  队列头部的胶囊会显示进度，跑完自动刷新结果板；
- **打开识图**：一键打开引擎入口，并把本地变体文件路径复制到剪贴板（直接拖进上传框），
  结果页内容或 URL 粘回来即可。

同一变体可以同时派发到多个引擎——索引互不重合，交叉验证才能判断「全网独一份」还是「只是某家没收录」。
服务重启时，残留的「搜索中」任务会被自动标记为失败（不会永远卡住队列）。

**队列筛选**（几百条待搜索时这是最常用的入口）：状态分栏之上再加一层多维筛选，每个筛选项都带**基数**：

| 维度 | 说明 |
| --- | --- |
| 种子 | 下拉选某个种子，标签显示「未跑/总数」 |
| 引擎 | 芯片形式，显示 `已产出/总数`，一眼看出**哪个引擎在这张图上没东西** |
| 变体类型 | 芯片形式（全图 / 中心裁剪 / 四分之一 / 灰度 / 边缘 / 手工框选…），同样带产出比 |
| 关键词 | 匹配种子标题、变体 label/kind、引擎名、备注 |
| 产出 | 「只看到有产出的」/「只看还没产出的」——找出**这一轮哪些变体真的捞到东西了** |

多个条件是与逻辑，可叠加（例：某个种子 + 百度 + 全图）。筛选**只影响列表显示**，不改动队列本身，
点「清空筛选」回到全部。筛选条件会拼进 `GET /api/queue` 的查询串，所以视图可以直接分享/收藏。

### 3. 三层去重与聚类

单靠一种相似度判断不了「是不是同一张图」：

| 层 | 方法 | 作用 | 阈值（可调） |
| --- | --- | --- | --- |
| 文件层 | 落盘原样保存；键 = 解码像素的 SHA-256 | 同一份文件再次出现（同一张图重复上传/重复转载） | 相等即命中 |
| 视觉副本层 | pHash（32×32 DCT，16×16 中值二值化，256 位） | 二次压缩、缩放、转存 | 汉明距离 ≤ 4 判同，≤ 14 进入语义确认 |
| 语义层 | 本机 SigLIP2，768 维归一化向量 | 同一主体/场景但不是同一张图 | 余弦 ≥ 0.93 判同，≥ 0.86 入簇 |

三层都过不了，才算「新的一张图」。被判为重复的结果不会被丢掉，而是**挂到已有视觉对象下当一个转载来源**——这样一张图被转载 100 次，结果板上仍然只是 1 个对象、100 条来源记录。

### 4. 来源聚合器（`vsw/engines.py`）

每个视觉对象下保留全部发现记录：来源 URL、域名、平台、页面标题、发现时间、引擎、图片直链、日期线索、可信度分级（archive / reference / ugc / curation / commerce / engine / unknown）。早期版本、存档站、论坛原帖会在「来源潜力」里获得更高分。

### 5. 发散度排序器：探索价值

```
E(i) = 0.30·Nᵢ + 0.25·Pᵢ + 0.25·Bᵢ + 0.20·Mᵢ
```

- **Nᵢ 新颖性**：与已收集语料的语义距离（语义层不可用时退化为感知哈希距离）。
- **Pᵢ 来源潜力**：来源是否可能追溯到原始页（archive > reference > ugc/curation > 引擎页），以及是否拿到标题、日期、原图直链。
- **Bᵢ 桥接价值**：是否来自尚未出现的平台，以及它在语义上是否靠近**别的**簇（能通向新主题）。
- **Mᵢ 元数据价值**：分辨率、体积、标签数、标题、日期线索。

四个权重在「指标与公式」页里可直接改，改完点一下就用新权重重算全库排序。**权重只是初始假设，应该按你自己筛出的高价值结果调整，而不是找通用最优值。**

### 6. 搜索链回放

每个结果都能追溯到它的发现路径：

```
种子图 → 裁剪版本 → 引擎检索 → 结果图 → 来源网页 → 回流成的新种子
```

在结果详情里以链路图给出，并标明哪一步带来了新来源、哪一步只是重复转载。

### 附带：三队列

排序结果被归入三个独立队列，而不是按相似度一股脑展示：

- **A 来源追踪**（相似度 ≥ 0.60）：找原图、不同分辨率、裁剪版、转载页。
- **B 主题扩散**（默认）：同期、同场景、同风格，能开出新搜索分支。
- **C 桥接探索**：探索价值高且带来新平台/新簇的桥接图。

阈值同样可调。

### 附带：入库归档（把一轮搜索「结案」）

结果板会越攒越长，翻不动，指标也被历史数据稀释。归档机制解决这个：

- **归档当前批次**：给当前活动结果留一份**快照记录**（对象数、来源数、平台数、三队列分布、
  覆盖日期、图片体积），然后把这些对象从活动结果板上收起来 —— 结果板重新变短，
  指标只反映「正在查的这一轮」；
- **只归档选中的图片**（可选）：在结果板上勾选卡片（「选为种子」就是勾选，按钮会变成
  `归档选中 N 个`），再点「入库归档」—— **选了几个就只归档几个**，其余留在板上继续查。
  没勾选时按钮回到「入库归档」，走整批结案。归档视图里每一批都能单独取消归档；
- **不是删除**：图片、来源页、缩略图都还在磁盘上；归档对象仍然可以按批次浏览、随时整体恢复；
- 归档期间它们**不参与**去重基准与语义索引（否则新一轮搜索会被上一轮的结果折叠掉），
  但**重复载体跟着它们的对象一起归档**，活动视图不会剩下孤儿转载；
- **归档口径一致**：预览数 = 实际归档数 = 批次快照里的数（整批与选中两条路径共用同一套快照逻辑，
  自测里分别断言）。

实测：整批一次 —— 活动结果板 24 个对象 / 72 条来源 / 7 个平台 → 批次 `#2`：预览 24 → 归档 24 →
快照 24，队列分布 `{diffusion: 20, tracking: 4}`；选中一次 —— 55 个对象里选 3 个 → 批次 `#3`：
预览 3 → 归档 3 → 快照 3，板上剩下 52 个，取消归档后回到 55 个。

### 附带：回收站（清理没选为种子的结果）

结果板会越攒越多，但真正有价值的是你**选为下一轮种子**的那批。所以有：

- **卡片上的「选为种子」就是选择器**——选中的卡片会高亮，`选中 → 回收站` 就把它们收起来；
- **`清理未选为种子`** 一键把所有**没被选为种子**的视觉对象收进回收站；
- 已回流的成果（`status='promoted'`）**默认受保护**，不会被一键清理带走；
- 回收站是**软删除**：记录、来源页、图片文件全部保留，`恢复` 一下就回到结果板；
- 收进回收站的对象不再出现在结果板、搜索图谱、语义检索和去重候选里（簇的质心也会重算）；
- 归档与回收站是**正交**状态：已归档的对象被移进回收站后，回收站里**仍然看得见**
  （不会被"归档"过滤掉）—— 否则它既不在归档列表、也不在回收站里，变成看不见也清理不掉的幽灵行。
  恢复后它回到归档视图，不会泄漏回活动结果板；
- 只有回收站里的页面能**彻底删除**（记录 + 图片文件 + 缩略图一起删），而且要求显式 `confirm`，
  防呆：没进过回收站的对象拒绝被彻底删除。

实测一次：结果板 77 个对象（其中 1 个已回流）→ 一键清理收走 76 个、已回流那个原地保留 →
恢复 1 个回结果板 → 彻底删除 1 个，`files_removed: 2`（原图 + 缩略图），文件确实从磁盘消失。

## 三、如何启动

```bat
:: 双击即可（会自动打开浏览器）
start_vsw.bat
```

或手动：

```bash
python -m vsw.server --root vsw/data --host 127.0.0.1 --port 8799
# 可选：--allow-private  只在本地自测时允许抓内网/回环地址的图
# 可选：--no-browser
# 可选：--protect       给这个工作区上锁（第一次会自动生成一把主人密钥）
# 可选：--unprotect     把锁摘掉
```

打开 `http://127.0.0.1:8799/`，七个工作区：

| 工作区 | 用途 |
| --- | --- |
| 种子图片池 | 拖拽/路径/目录/URL 导入，选变体与引擎，导入即入队；卡片上有**框选搜索**（Lens 风格选区） |
| 批处理队列 | 待办/搜索中/待复查/失败分栏；**自动识图**（无头浏览器，百度/360）与「打开识图」手动派发、结果回填 |
| 结果板 | 三队列 + 探索价值排序；卡片可「选为种子」批量回流，也可**选中 → 回收站**、**入库归档**、或一键**清理未选为种子** |
| 语料检索 | 本机 SigLIP2 文字→图语义检索（搜自己攒下的语料，0 成本） |
| 来源与聚类 | **入库归档**（批次快照 / 查看 / 取消归档 / 修来源标注）、**回收站**（恢复 / 彻底删除 / 清空）、视觉簇、平台分布 |
| 搜索图谱 | 种子→变体→结果→来源 的可视化网络（滚轮缩放、点击进详情） |
| 指标与公式 | 权重/阈值可调，按引擎/按变体（含手工框选）/按天产出，操作台账 |

手机端在 `/m/`（见下面「手机版」一节），不占用上面这七个工作区。

依赖：Python 3.10+、`Pillow`、`numpy`、`requests`（都已在本机可用）；
自动识图另需 **Node 18+**（本机 22/24 都有，驱动只用标准库 + 全局 `WebSocket`）与本机 Edge/Chrome。
语义层需要本机模型 `D:\siglip2-base-patch16-224`；**没有它也能跑**，工作台自动退化为文件层 + 感知哈希层，公式与队列照常工作。

### 让不在同一个局域网的人也能打开

局域网地址只在一个网里能用。本机已装 Tailscale 的话，服务可以自己开一条公网通道：

```bat
python -m vsw.server --root data --host 0.0.0.0 --port 8799 --tunnel    :: 开
python -m vsw.server --root data --host 0.0.0.0 --port 8799 --no-tunnel :: 关
```

页面里也能点：右上角「共享 / 账号」→「不在同一个局域网 / 别的城市」→「打开公网通道」
（只有主人能点）。启动日志会打印 `🌍 公网地址：https://<节点名>.ts.net/`。

- **先有门槛才能开**：没账号也没密钥时会拒绝（400 +「先建第一个账号…再开公网」）。
- **经隧道进来的人算外部设备**：Funnel 回源的对端固定写成 `127.0.0.1`，真实来源在
  `X-Forwarded-For` 里，所以 `Handler._is_local()` 先看这个头 —— 否则整个互联网都能
  抢先建出主人账号。
- 手机端登录后「我的」页会显示这条公网地址，一键复制。

### 分人用：账号、私人工作区、协作

默认不设防（本机与同一局域网都能读写）。要分人用，就在页面顶栏右上角（或「共享 / 账号」面板里）
**建第一个账号** —— 建完这份数据就归它名下。

- **「跑服务的那台电脑」按机器判断，不按回环判断**：用 `127.0.0.1` 能建，用**这台机器自己的
  局域网地址**（`http://192.168.1.46:8799/`）也能建。依据是"对端 IP 属于本机网卡吗"，
  真·远程设备（手机、别人的电脑）仍然只能看到一句说明 —— 谁能第一次建号，谁就是主人。
- **一个工作区 = 一个数据目录**：自己的 `workbench.sqlite3` + `media/` + `archives/`，
  不是"同一张表按 owner 过滤"的假隔离。老数据目录原地留下，成为第一个账号的工作区。
- **三种角色**：主人（全部权限）/ 可操作（搜、导、归档、进回收站）/ 只看。
  权限在服务端判，前端藏按钮只是顺手。
- **邀请码**：`INV-XXXX-XXXX-XXXX`，一次性、带有效期、**不能直接发主人**；注册入口不对外开放。
- **访客密钥**（`VSW-XXXX-XXXX-XXXX`）保留给"只想给人看一会儿"的场景，是工作区局部的，
  而且进不了账号接口。

登录状态两种携带方式：普通浏览器走 cookie；APK 里页面是 `file://`，带不了 cookie，
所以登录后会存一份令牌走 `X-VSW-Session` 请求头（访客密钥走 `X-VSW-Key` 或 `?key=`）。

实现位置：[`vsw/accounts.py`](accounts.py)（账号/工作区/成员/会话/邀请码）、
[`vsw/hub.py`](hub.py)（工作区句柄表）、[`vsw/access.py`](access.py)（访客密钥）、
[`vsw/server.py`](server.py) 的 `_resolve/_bind/_guard`（每请求定身份 + 绑工作区）。

**加了身份之后，所有"绕开请求头"的通道都要查一遍。** `<img>` 带不了头、`<a download>` 带不了头、
裸 `fetch` 忘了带 —— 这三处第一次上线就各踩了一次：手机端补缩略图用裸 `fetch` 取 `/media/`，
开了账号之后全 401 又被 `continue` 掉，表现是「列表一片空白、控制台没有红字」；归档 zip 走
`<a download>`，同样 401。现在取图统一走 `netFetch()`，直链统一定 `withKey(url)`
（会话令牌优先、其次访客密钥，`?sid=` / `?key=`，服务端两种都认）。

**语义模型只有一份。** 工作区各占一个数据目录，但 `VisionEngine` 是 `VisionEngine.instance()`
的全进程单例（`[engine.py](engine.py)` 的 `_lock`/`_instance`，`[service.py](service.py:75)`
`self.vision = vision or VisionEngine.instance(...)`）：权重只加载一次，向量存各自库里。
开多少工作区都不增加模型内存，`/api/health` 里的 `vision.available` 对所有工作区一致。

### 手机版（PWA / 安卓 APK，可离线独立使用）

手机端不是"把桌面网页缩小"，而是一个**自己的本地库 + 可离线用的 App**。
同一份 `static/mobile/index.html` 有两种派发方式：

- **手机浏览器直接开**（PWA）：发个网址，添加到主屏即可，不用装东西；
- **装成 APK 发给别人**：见 [vsw-android/README.md](../vsw-android/README.md)
  —— 手工编译链（不需要 Gradle/Android Studio），354 KB，自带首次启动引导与原生扫码。

```bat
:: 双击 start_vsw_lan.bat，或给 start_vsw.bat 加 --lan
python -m vsw.server --host 0.0.0.0 --port 8799
```

然后手机连同一个 WiFi，打开 `http://<电脑IP>:8799/m/`，浏览器菜单里「添加到主屏幕」。
启动日志会打印候选地址和**可以直接扫的二维码**（终端里用半块字符画的）：

```
[vsw] 手机端（同一 WiFi 下打开）：
[vsw]   http://192.168.1.46:8799/m/  ← 二维码用这个
[vsw]   http://192.168.137.2:8799/m/
[vsw]   这台机器有多个网卡，手机扫上面的码连不上时，把其它地址手打进去试试
```

**⚠ 安全边界（先说清楚）**：`--host 0.0.0.0` 会让**同一 WiFi 下的任何设备**都能访问这个工作台，
而工作台**目前没有口令**。在家里 / 自己的手机热点上没问题，**别在公共 WiFi 上这么开**。
默认（不加 `--host 0.0.0.0`）只监听本机、手机连不上 —— 这是刻意的默认值。要加访问口令说一声。

**为什么手机需要一个"本地库"**：手机跑不了无头浏览器，所以**「自动识图」只能由电脑执行**。

| 手机能离线做的 | 手机做不到的（离线时明确标灰并写明原因） |
| --- | --- |
| 浏览结果板（三队列筛选、搜索、排序） | 自动识图（要电脑上的无头浏览器） |
| 看详情：大图、来源聚合、**搜索链回放** | 「打开识图」派发结果页 |
| 拍照 / 相册导入、**手机上直接框选** | 语义检索（SigLIP2 在电脑上） |
| 归档、回收站恢复 / 清理 | 修来源标注等维护动作 |

实现要点：

- **快照同步**：`GET /api/mobile/snapshot` 一次拉下种子/变体/对象/队列/归档/回收站 + 评分权重，
  图片按需下载成 Blob 独立存（**不把 base64 内联进 JSON** —— 那样 IndexedDB 会膨胀且无法流式/缓存）；
- **三种图片档位**：只带缩略图（推荐）／连原图（可彻底断网看图，体积大）／只带文字；
- **快照默认不带来源明细**：实测这一项占快照 60%+（200 条回收站每行 2.9 KB 的来源数组）。
  默认只给 `source_count`，点开详情时按需取那一条并缓存回本地库；要一次性打包时用 `?sources=1`。
  真实库实测（`limit=200`）：明细版 763 KB、精简版 555 KB、不含回收站 243 KB；
- **离线收件箱**：手机上拍/选的图、框选结果、离线时删掉的对象都先存本地，
  回到同一 WiFi 点「推回电脑」一次提交（`POST /api/mobile/sync`）。推回走的是工作台既有管线，
  所以三层去重、聚类、排序照常工作；
- **数据集导出/导入**：整个本地库（含缩略图）导出成一个 JSON 文件，用数据线或微信传给另一台手机，
  完全不经过网络；
- **单文件外壳**：手机端全部 HTML/CSS/JS 内联在一个 `index.html` 里（不依赖外部 `app.js`/`app.css`），
  service worker 把它整个缓存住 —— 装到主屏后即使连不上电脑也能打开，读的是本地库；
  四个文件手工拷到手机也不会漏。

手机上独有的两件事：**框选比鼠标顺手**（拖框 / 拖四角 / **双指捏合缩放整个选区** / 双击清空），
以及**拍照即入库**（后置摄像头直连，相册可多选）。手机端的「回收」也走工作台那道保护闸：
误删已回流的成果会被拒绝并说明原因。

### 手机端也能筛选和删除队列项

手机端原来只有状态栏和引擎筛选，也没法删队列项 —— 队列几百条时很难操作。现在补齐：

- **筛选**：状态（待处理/待搜索/待复查/已完成/失败）+ **种子**（下拉，带「已产出/总数」）
  + **引擎**芯片 + **变体类型**芯片 + **关键词**（引擎/变体/种子标题/备注）+ **产出**
  （只看到有产出的 / 只看还没产出的）。芯片上带 `2/36` 这样的基数，一眼看出哪一项筛出来有东西；
  摘要会写明当前叠加了哪些条件、筛出多少条。
- **删除**：
  - 卡片上的「删除」（一次确认；只删队列记录，已产出的结果与种子不受影响）；
  - 顶部「删除筛选结果（N）」—— 删的正好是当前筛选出来的那批；
  - 「选择」进入多选（或长按卡片进入），逐条点选后「删除选中」，可「全选本页」；
  - 离线时这些按钮会明确提示"需要连上电脑"，不会静默失败。
- 删除后用 `/api/queue` 重新拉一遍队列写回本地库，界面与电脑保持一致（不留幽灵条目）。

对应接口：`POST /api/queue/delete`，`{job_ids: [...]}` 批量删除，或 `{statuses: [...]}`
按状态清空（等同于 `/api/queue/clear`）。

### 手机上看不到"归档文件夹"怎么办：保存到手机

真机反馈：归档卡片上点了「归档文件夹」，手机上什么也看不到。
两个原因叠在一起：那个按钮只是**让电脑弹资源管理器**（手机本来就看不了电脑目录），
而且 APK 里的 WebView **没有设 `DownloadListener`** —— 任何下载链接点下去都是静默无效。

现在归档卡片有三个按钮，各管一件事：

| 按钮 | 在哪生效 | 作用 |
| --- | --- | --- |
| 查看（N） | 手机本地 | 列出该批对象（缩略图 + 标题 + 来源数），离线也能看 |
| **保存到手机** | 手机 | 把整批打包成 zip 下载到手机的「下载」目录 |
| 在电脑上打开 | 电脑 | 落盘并在资源管理器里打开（路径会显示成"电脑上的文件夹：…"） |

「保存到手机」拿到的是一个 zip：`imgs/` 里是该批图片，`manifest.json` 是清单。
手机的文件管理器、解压 App、微信传文件都能直接用。

配套改动：

- 服务端 `GET /api/archive/{id}/zip`（`data/archives/<id>-<名字>.zip`，文件比缓存新就重建）。
  中文文件名按 **RFC 5987** 放进 `filename*=UTF-8''…` —— HTTP 头只能是 latin-1，
  直接写中文会让服务端在发响应头时抛 `UnicodeEncodeError`；
- 服务端补了 **`HEAD`**（以前一律 501，于是"先探一下大小"的客户端直接失败），
  并加了 `Access-Control-Expose-Headers`，让跨源的手机页面能读到 `Content-Length`
  与 `Content-Disposition`；
- APK 加了 `DownloadListener`：用系统 `DownloadManager` 存到「下载」，完成时给通知；
  文件名优先取 `filename*` 里的中文名（否则会变成无意义的 `archive-15.zip`）。

### 归档现在有"自己的文件夹"，手机也能打开批次

原来的问题：归档只打状态标记，图片仍散在 `media/results/`，**没有"这一批的文件在哪"这回事**；
手机上更是只有一个「取消归档」，完全打不开批次看内容。

现在：

- **每批落盘一个文件夹**：`data/archives/<批次id>-<名字>/`
  - `imgs/` 里是该批对象的图片。**用硬链接**（`os.link`，同一卷不占额外空间），
    硬链接失败才退回复制；
  - `manifest.json` 是清单：每个对象的标题、三分类、发散度、相似度、尺寸、引擎，
    以及**每条来源的 URL**，方便直接拿这批图去别处用；
  - 幂等：再导出一次只补新增的，已有文件记为 `reused`。
- **电脑端**：归档批次行上多了「归档文件夹」—— 落盘并在资源管理器里打开。
- **手机端**：批次卡上多了两个按钮
  - 「查看（N）」：列出该批的对象（缩略图 + 标题 + 来源数），点一条看详情。
    归档对象也进了快照（`archived`），所以**离线也能看**；
  - 「归档文件夹」：让**电脑**生成并弹出那个目录（手机自己打不开电脑的目录），
    并把路径显示出来。离线时提示需要连上电脑。
- 接口：`GET /api/archive/{id}/paths?export=1`（生成 + 返回路径与文件清单）、
  `POST /api/reveal {path}`（在服务器那台电脑上打开）。
  `reveal` **只允许数据目录以内的路径**，避免变成任意程序启动器。

关于隐私/权限的说明：`reveal` 会在服务器上启动资源管理器，所以它和整个工作台一样，
只应该跑在你自己的可信局域网里（本来就没有鉴权，README 里一直这么写）。

### 手机端导入为什么会"没进队列"（已修）

三个原因叠在一起，都修了：

1. **只有新种子才入队**：`import_bytes` 里入队写在 `if created:` 里 —— 导入一张
   **已经存在**的图（像素哈希命中种子池）时会静默什么都不做，只回一句"已建成种子 #N"。
   现在重复导入也会入队；`store.enqueue` 对 (变体 × 引擎) 是幂等的，已存在就复用
   （失败状态还会被重置为待搜索），所以不会制造重复任务。
2. **导入后没有刷新队列**：手机端导入成功后没有重拉队列，队列页还是旧数据。
   现在每导入一张就静默刷新一次，提示里直接写「入队 N 条」；
   「全部导入」结束时汇总一次（`导入完成：3/3 张成功 · 待处理队列 N 条`）。
3. **快照的队列上限太小**：快照用同一个 `limit`（默认 300）同时截断结果与队列，而队列条数
   通常是结果的几倍（一次导入 × 16 个变体）。新任务按 id 升序排最后，就被截断掉了。
   现在队列单独用 `max(1200, limit*4)`，且**同状态下最新在前** —— 刚导入的任务出现在顶部。
   手机端手动刷新（`/api/queue`）也在客户端做同样排序（桌面仍保持 id 升序的 FIFO 派发语义）。

顺带加了「入队变体」选项：手机快拍默认**仅全图（每张 1 条）**，需要全套变体时再切
「全部变体（每张约 16 条）」。这个选择会被记住。

### 手机端也能按引擎批量清理

队列页的「按引擎清理」预设：把某个引擎的**待处理**任务整批删掉，一个按钮一步完成
（例如 so360 长期被验证码挡着，那批待搜索只是噪声）。预设只列确实有待处理任务的引擎，
并显示条数（`清 so360 待处理 84`）；确认框会说明只删队列记录，已产出的结果和种子不受影响。

| 手机端接口 | 作用 |
| --- | --- |
| `GET /api/mobile/snapshot` | `images=thumbs\|full\|none` + `limit` + `trash=0/1` + `sources=0/1` → 离线快照 |
| `POST /api/mobile/sync` | `{imports:[{name,data_url,auto_enqueue,engines}], trash:[id,…]}` → 把手机上的操作合并回工作台 |
| `GET /api/mobile/qr.png` | 当前局域网地址的二维码（手机设置页直接显示它） |

APK 版把上面这套页面打进 `assets/mobile/index.html`，用 `file://` 装载。
**已经实测**（同 Blink 内核）：`file://` 页面可以 fetch/XHR 到 `http://<局域网IP>`，
也可以用 IndexedDB —— 所以 APK 里不需要 service worker 也能连电脑、也能存离线库。
细节与"还没验证到的部分"见 [vsw-android/README.md](../vsw-android/README.md)。

### 结果图为什么会「全部消失」（r23）

**注意：我一开始把原因判成「防盗链 403」，这是错的。** 拿库里 549 条真实引擎图地址实测，`mms0/1/2.baidu.com` 与 `p0.ssl.qhimgs1.com` 在带不带 `Referer` 时都回 200。所以「图全部消失」更可能是**我们根本没抓到图**（`similar` 为空 → 面板落到「没抓到相似图」，于是既没图也没统计行）。

r24 因此先加诊断：结果为空时把提取脚本的 `diag` 写成一句人话（`pcsimi 请求 N 条 · 页面图片主机 mms0.baidu.com×12`），面板标题带上版本号，抽图规则从「只认几个域名」放宽成「≥96px 的图都要」。

所以改成**原生带 Referer 去取图**：`WebSearchActivity.finishWithThumbs()` 在结果命中后起一个线程，对前 12 张调 `fetchThumb()`（`HttpURLConnection` + `Referer: <引擎页>` + 移动 UA，先 `inJustDecodeBounds` 再 `inSampleSize`，压成 360px / JPEG 72，单张上限 6 MB），把结果塞进每条 `d` 字段（data URL）。页面用 `x.d || x.u` 渲染，并在统计里如实写「其中 N 张已存成本地小图」；一张都没取回来时明说「引擎拦了请求，可以复制图片链接自己在浏览器里看」。

代价：多 1–2 秒、结果 JSON 大 200–400 KB，所以上限卡 12 张 / 360px。

### 手机自己搜（半自动，r19）

批量那条路要电脑。电脑不在手边时，APK 里的队列项还有一个「手机搜」：原生把图交给
WebView 里的引擎页面（`onShowFileChooser`），你在页面上点一下上传，引擎自己传图、自己跳结果页，
提取脚本把结果抓回手机。**不能全自动**是因为浏览器规定文件选择器必须由用户手势触发 ——
后台 `input.click()` 打不开它，这一点没得绕。

### 手机上怎么更新到新版

电脑上换了新包以后，手机上不用再传文件：

```
python scripts/vsw-publish-apk.py --notes "这一版改了什么"
# 或者直接跑 vsw-android\build_release.bat —— 它打完包会自动发布
```

包和 `version.json` 落在 `<root>/dist/`。手机端「我的 → 检查更新」问
`GET /api/app/version?build=<当前版本>`，有新版本就显示「下载并安装」：下载、校验 SHA256、
再交给系统安装器（安装框得你自己点一下 —— Android 不允许应用静默安装）。
本地没有包时会兜底去问 GitHub Releases（`--gh OWNER/REPO`）。

### 断联电脑：手机上也能导入、也能搜（r21）

以前断开电脑导入一张图，队列里既没有它也没有缩略图，必须先同步电脑 —— 因为离线那一支只
把图塞进 `pending` 收件箱，本地不建种子、不建队列项。现在离线导入就地建：

- 一条本地种子 + 一条本地队列项 + 两张本地图（320px 缩略图、原图）；
- id 用**负数**（存在 `meta.localSeq`），不会和电脑上的 id 撞；
- 队列页看得见缩略图、条目上标着「手机上」，「手机搜」直接用本地原图，全程不需要电脑；
- 离线也能删，删的时候连带把「等回连后推给电脑」那条一起清掉；
- 回连后 `flushPending()` 推给电脑进正式库，推成功就删掉本地影子记录，不会变成两条。

同时修了两个「同步一次就没了」的地方：`refreshQueueFromServer()` 与 `syncSnapshot()` 在清空本地
仓之前，都要把 `local: 1` 的种子/队列项留出来，写完服务端数据再补回去。

### 扫码闪退的两个原因（r22）

APK 里点「扫码」会闪退。第一个原因是清单里**没声明** `QrScanActivity`：类编译进了 dex，但
`startActivityForResult` 找不到可启动的组件，抛 `ActivityNotFoundException`，没人接就崩。
第二个原因在扫码页自己身上：它用 `takePicture` 的 JPEG 解码，而那是**照片**分辨率（小米 9 默认
4000×3000），一张 48 MB 位图 + 48 MB 像素数组，MIUI 上很容易 `OutOfMemoryError`；而 OOM 是
Error，`catch (Exception)` 接不住。

现在：清单补上并锁竖屏、`pickPictureSize()` 把拍照尺寸压到 ≤200 万像素、解码按 `inSampleSize`
缩到 800px 内、解码线程 `catch (Throwable)`、`openScanner()` 再兜一层 try/catch
（打不开就提示手填地址）。

### 手机端的「自动搜图」（电脑干活，手机下单）

手机的 WebView 里没有能替引擎上传一张图的内核 —— 那条链路要真实的文件选择框和真实 XHR。
所以手机端的自动搜图是「派活」：

```text
队列页 →「自动搜图（N）」 → POST /api/auto/run → 服务端排班线程逐个跑 browser_search()
                                            ↘ 手机每 2.5s 拉 /api/auto/state 看进度
```

可以按下去就关屏，回来再看结果；跑完手机端自动重拉队列与快照。

- 候选只收**真能自动识图**的引擎（实测 `baidu`、`so360`），其它引擎单独计数成
  `skipped`，不会混进来制造失败任务。
- **一次只跑一批**：一台机器一次只能开一个识图页。
- **一个任务失败不中断整批**，失败原因（如「被验证码挡了」）直接显示在手机上。
- 结论提示在刷新之后弹出 —— 否则会被「同步完成」盖掉。

> 依赖：电脑上要有 Node 18+ 与 Edge/Chrome（`/api/health` 里的 `browser.available`）。
> 手机端离线时按钮是灰的，并写明「手机自己跑不了无头浏览器」。

## 四、衡量成功的指标（结果板 → 指标页）

不看搜索次数，看**每 100 次搜索操作换来多少真正扩网的东西**（一次操作 = 一次派发到引擎的检索）：

- 每 100 次操作新增多少张**不重复**图片
- 每 100 次操作新增多少个独立来源
- 每 100 次操作新增多少个此前未探索的平台
- 平均多少次操作才发现一个新来源
- 已折叠的重复转载数（以及「不去重会显得发现了多少张新图」）

## 六、开发过程中实测出来的三个「坑」（都已修好，写在这里免得再踩）

1. **JPEG 没有不动点，所以「存一份、哈希另一份」是错的。** 同一张图反复解码重编码，长度会一直漂移
   （实测 11472 → 11495 → 11516 → 11515 → 11506 → …，永远不收敛）。这种写法会产生**以后再导入同一张图
   也永远对不上的键**，文件层去重等于失效。
   现在：**落盘原样保存**（不重编码，画质与体积都不动，实测每张 ~95 KB，与原始素材同量级），
   去重键用**解码像素的 SHA-256**——把落盘字节再导入一次，字节相同、解码相同，键必然相同。
   「同一张图的不同压缩版本要算同一个身份」这件事交给感知哈希层和语义层（它们本来就是干这个的），
   而不是硬塞进文件层。

2. **64 位 pHash 分不开几何变体。** 经典 8×8 DCT 块把「四分之一裁剪」和「全图」哈希成同一个值，
   去重层会因此变瞎。改成 16×16 块后 13/13 几何变体互不相同（仍是 64 位，但因为总位宽 256 位，
   **哈希列必须存 TEXT**——塞进 SQLite 的 64 位整数列会被静默降级成浮点、丢掉低位）。
   判同阈值 4 位，位于实测噪声底（同图一次编解码往返 ≤ 2 位）与异图（20 位以上）之间。

3. **取不到的图绝不能入库。** 早期版本在下载失败时仍然建一条空记录，结果板会出现 0×0、
   没有来源、也无法回流的幽灵条目。现在取图失败一律记进 `failures` 并如实报告；
   内联 `data:image/...` 候选也能正常解析（`_clean_url` 曾经把它们当非法 URL 丢掉，导致结果页只剩 1 条候选）。

## 七、已知边界

- **自动化程度因引擎而异，而且是探测出来的**：百度识图可全自动，而且能拿到相似图的**真实来源页**
  （走 `/ajax/pcsimi` 的 `fromUrl`，实测 30/30 有归属）；360 识图同法可用，但它会对本机 IP 弹验证码；
  Bing 的「以图搜图」已经不可用（`imgurl:` 深链被当文字搜索、`searchbyimage/upload` 返回 404、
  `visualsearch` 把图送去 OCR），工作台据此把它降级为失效引擎并拒绝入队。
  证据见 [`NOTES-engines.md`](NOTES-engines.md)。
- **百度的来源页靠 XHR 拿，不靠 DOM**：结果页渲染出来的 30 个卡片只指向百度自己的看图器，
  但页面自己发的 `/ajax/pcsimi` 响应里每条都带 `fromUrl`（真实来源网页）。工作台抓下这条请求、
  在页面里回放它（签名/session 由页面生成，必须回放才过），所以百度的产出**有来源归属**：
  实测一次检索 30/30 条都有来源页（大众点评 19、小红书 2、去哪儿 2、花瓣 2…）。细节见
  [`NOTES-engines.md`](NOTES-engines.md)。
- **没有独立的「相似站点」接口**：`/ajax/pcsites`、`pcsame`、`pcsource`、`pcfrom`、`pcpage`、`pcgoods`
  实测全是 400；不过 `pcsimi.fromUrl` 已经把来源页给到了，所以那条路不再必要。
- **语义判同阈值需要校准**：SigLIP2 的余弦普遍挤在 0.85~1.0。本机实测「同图不同压缩」约 0.97，
  所以判同用 0.93。换模型或换成截图/文字类素材时应重新校准（阈值在「指标与公式」页可调）。
- **聚类是单遍的**：按质心相似度增量入簇，不重跑全局聚类；删掉大量结果后建议重算一次语义索引。
- **回流会保留原文**：把结果提升为新种子时用的是本地已落盘的那一份（`media/results/…`），
  所以即使原图 URL 之后失效，回流出来的种子依然是完整可用的。
- **存储是原样保存**：不重编码，所以一张 700×525 的图落盘约 95 KB（不是几百 KB 的 PNG，
  也不是二次压缩后掉画质的 JPEG）。代价是「同一张图的不同压缩版本」在文件层不算同一个键——
  这由感知哈希层与语义层负责，文件层只负责「同一份文件又出现了」。
- **浏览器是单实例的**：同一时刻只跑一个自动识图任务（避免多个无头 Chromium 抢资源、也避免把引擎
  打到限流）；队列里其余项照常可以手动派发。

## 手机搜到的图为什么只进得去 8 张、还全是无关图（r25）

三件事一起修：

1. **结果没有出口。** 面板只有「复制图片链接」，看完就没了 —— 结果板里当然不会有这些图。
   现在多一个「存进结果板（N）」：联网时走 `POST /api/mobile/sync` 的 `imports` 通道（服务端
   `apply_mobile_sync` → `import_bytes(kind="mobile-import")` 建种子），断网时先写进手机
   待同步队列，联网后自动推。
2. **图源看不出来。** 面板现在永远写一行「图源：引擎接口（pcsimi）」或「图源：页面里捡的
   （接口没捕到）」。前者是能反查来源页的正经结果，后者是 DOM 兜底，命中率低得多 ——
   一眼就能判断这次搜到底走通了没有。
3. **抽错了区域。** 上一版把尺寸门槛放到 96px，于是「猜你喜欢 / 热门推荐 / 页脚」里的
   大图全被当成结果。现在门槛回到 150px，并且往上找祖先容器，`recommend|hot|guess|footer|
   header|nav|sidebar|banner|ad|related` 命中的整块跳过。

`scripts/vsw-probe-phone-search.js` 加到 28 项（新增：按钮文案带张数、点完明确说存了几张、
断网时进待同步队列、待同步里带的是内嵌 data URL、面板写明图源）。
